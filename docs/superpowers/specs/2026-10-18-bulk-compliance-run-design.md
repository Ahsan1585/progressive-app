# Bulk Compliance Analysis & Auto-Generate — Design

## Problem

Billing specialists currently review one practitioner at a time: lock, open Compliance Analysis, wait for auto-approve of clean sessions, manually Generate & Issue. For a tenant with hundreds of practitioners, this doesn't scale — most practitioners' sessions match EIMS cleanly and need no human judgment at all.

## Goal

Let a billing specialist select many practitioners (or "select all") within one chosen billing period (Biweekly 1, Biweekly 2, or Monthly) and run compliance analysis across all of them in one action. A practitioner whose entire selected period is clean (every session matched, unflagged, no duplicate) automatically generates its SEVF + invoice and moves to Completed Bills — no human touches it. A practitioner with any flag, mismatch, duplicate, or missing-in-EIMS session in that period is left untouched in Pending Bills, exactly as today, for a specialist to lock and resolve by hand.

## Non-goals

- No change to invoice/SEVF document shape — still one batch per practitioner per period, as today (`billing_batches.practitioner_id` stays a single FK).
- No new review-queue UI — flagged practitioners surface in the existing Pending Bills screen, same lock/Compliance Analysis/Approve flow.
- No change to how an individual practitioner is reviewed by hand; the manual single-practitioner flow is untouched.
- "All-or-nothing clean" is scoped to the one period selected on screen — a practitioner's Biweekly 2 or Monthly data is a separate, independent decision from their Biweekly 1.

## Behavior

1. Specialist selects a period (existing Biweekly 1/2/Monthly picker, unchanged) and selects practitioners via checkboxes (or "Select all") in the practitioner queue.
2. Clicks "Run Compliance Analysis (N selected)".
3. Backend processes each selected practitioner in turn:
   a. Attempt to lock (`review` scope). If already locked by someone else → skip, record as `skipped_locked`, continue to next practitioner. (No error, no blocking the rest of the run.)
   b. Run compliance analysis (reusing `getComplianceAnalysis`'s matching logic) scoped to the selected period's sessions only.
   c. If every session in that period is matched, unflagged, and has no duplicate → run the existing `generateNJEISForms` then `generateFinancialInvoice` pipeline for that practitioner/period. Release the lock. Record as `auto_generated`.
   d. If anything is flagged, mismatched, a duplicate, or missing-in-EIMS → release the lock without changing any session status. Record as `needs_review`. Sessions stay `pending`, visible and lockable in Pending Bills exactly as today.
4. Return a summary `{ autoGenerated: [...], needsReview: [...], skippedLocked: [...] }`. Frontend shows a result toast and refreshes the practitioner list.

## Data/API changes

- New endpoint: `POST /api/billing/bulk-compliance-run`
  - Body: `{ practitionerIds: number[] | 'all', startDate, endDate }` (period bounds, same shape the existing per-practitioner endpoints already take).
  - Gated by the same permission as Pending Bills (`billing_pending`).
  - Response: `{ success: true, autoGenerated: [{practitionerId, name, batchId}], needsReview: [{practitionerId, name, flagCount}], skippedLocked: [{practitionerId, name, lockedByName}] }`.
- `getComplianceAnalysis`'s core matching logic (session/state-row pairing via `assignGroupCandidates`, `buildFieldsForSession`, duplicate detection) is extracted into a shared function, callable both by the existing HTTP handler (response shape unchanged) and the new bulk endpoint. No behavior change to the existing single-practitioner Compliance Analysis tab.
- "Clean" for the purposes of auto-generate = matched && !flagged && no duplicateOfSessionId for every session in the selected period, AND no `missing_from_eims` (unmatched) session. This is intentionally the *strict* definition — a duplicate counts against cleanliness here even though today's single-session Approve gate doesn't check it server-side (known existing gap, called out below).

## Known gap being closed (small, aligned fix)

Today, `updateLogStatus` (the single-session Approve endpoint) doesn't check `duplicateOfSessionId` server-side — only the frontend blocks Approve on a duplicate. Since bulk auto-generate is unattended and must be strict, its "clean" check includes the duplicate test. As a small aligned fix, the same duplicate check is added to `updateLogStatus`'s server-side gate so the two paths agree (a duplicate can never be Approved through either path without a human explicitly resolving it first).

## Concurrency / locking

- The bulk run acquires the `review` scope lock on each practitioner immediately before processing them, and releases it immediately after (whether auto-generated or flagged for review) — never holds locks for the whole run, only the specific practitioner currently being processed.
- If a practitioner is already locked (by a human mid-manual-review, or another bulk run in flight), they're skipped for this run — not retried, not blocking the rest of the batch.
- This means two billing specialists can safely run "select all" at the same time without double-processing the same practitioner; whichever one gets the lock first processes that practitioner, the other sees it in `skippedLocked`.

## UI changes

- `BillingBatchReview.jsx`: add a checkbox per practitioner card (Set-based selection, mirroring the existing pattern in `RegisterPractitionerForm.jsx`'s bulk-invite bar) plus a header "Select all" control, scoped to the currently-selected period.
- A bulk action bar appears when ≥1 practitioner is selected: "Run Compliance Analysis (N selected)" button.
- On completion: a result toast summarizing auto-generated / needs-review / skipped-locked counts, then the practitioner queue refreshes (auto-generated practitioners disappear from Pending Bills into Completed Bills; flagged ones remain as normal "Needs review" cards, unchanged from today).
